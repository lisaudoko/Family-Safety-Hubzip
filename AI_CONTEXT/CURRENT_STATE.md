# Current State

_Last updated: 2026-07-10_

## Status

Feature-complete MVP+ in active development. Mobile app (Expo) + Express API + PostgreSQL all functional. Not yet published to app stores.

## Completed Major Systems

- **Auth**: parent register/login (bcrypt + UUID Bearer sessions, 90-day TTL at issuance, enforced at request time by `requireAuth` since 2026-07-10), child PIN login via family code, forgot/reset password, offline `local_` accounts with background server sync. Email verification: DB table + `email_verified` column exist, but no verification endpoints/flow are implemented.
- **Education**: 9 courses, 64 lessons, 13 quizzes, 22 badges, weekly tips (snapshot of mobile `data/seed.ts` as of 2026-07-08; DB counts may differ). Content lives in DB (`courses`/`lessons`/`quizzes`/`quiz_questions`/`badges`/`weekly_tips` tables) served via `/api/curriculum`; mobile also has static seed in `data/seed.ts`.
- **Assessment**: 10-question Social Media Readiness Assessment with per-category scoring (client-side, seed data).
- **Family**: family CRUD, children profiles (age bands), family technology agreement builder, family code for child login. Child accounts now get a role-aware Family tab: `GET /api/family` returns a self-excluded `siblings` list alongside `parents`/`children`, and `GET/PUT /api/family/agreement` are family-scoped via session `familyId` (children can read, only parents can write) — see 2026-07-10 entry in `AI_CHANGELOG.md`.
- **Challenges**: 8 family challenges with step tracking.
- **Devices**: device registration, heartbeat sync, screen-time/activity/education-activity event reporting, parent analytics (`screen-time`/`activity`/`education`/`summary`) + dashboard endpoints. Ownership validation (owner-or-family-parent gating on GET/PATCH/DELETE, owner-only on heartbeat/events) and a platform-neutral capability model (`lib/capabilities.ts`) were already implemented; verified and regression-tested 2026-07-10 (previously understated in `NEXT_TASK.md`). Education activity (lesson/quiz/challenge/assessment completions) now has its own `education_activity` event type/`lesson_participation` capability, distinct from general app `activity` events — see `AI_CHANGELOG.md`.
- **Devices**: device registration, heartbeat sync, screen-time/activity/education-activity event reporting, parent analytics (`screen-time`/`activity`/`education`/`summary`) + dashboard endpoints. Ownership validation and platform-neutral capabilities remain implemented. **Device Restrictions** (2026-07-10, Priority 5 groundwork): `GET|PATCH /api/devices/:deviceId/restrictions` lets a parent store per-device screen-time-limit/bedtime/block-Safari/block-new-installs/block-explicit-content/require-approval settings (`device_restrictions` table, `services/deviceRestrictions.ts`), family-ownership-checked (404 cross-family) and Zod-shape-validated; surfaced per-child on each child's detail screen (`app/child/[id].tsx`, via `useDeviceRestrictions` — relocated 2026-07-10 from a flat family-wide device picker on the Profile tab; devices are renameable in place there too via `apiUpdateDevice`). Storage of parent intent only — nothing enforces these on-device yet (see `docs/POLICY_ENGINE.md`). Two related tables (`device_app_rules`, `blocked_app_events`) exist in schema but are unwired — flagged as follow-up. **Family & Child Policies** (2026-07-10): `family_policies` (one per family) and `child_policies` (one per child) tables store the same field set as `device_restrictions`, via `GET|PATCH /api/family/policy` and `GET|PATCH /api/family/children/:childId/policy` (parent-only, family/child-ownership checked). Storage only; intended precedence (family < child < device) is documented in `docs/POLICY_ENGINE.md` but not coded — no rule evaluation engine exists. Child-level policy now has a mobile UI (each child's detail screen, via `useChildPolicy`); the family-wide policy endpoint still has none.
- **AI Coach**: chat endpoint with 10-message free-tier limit per period (`coach_usage` table); mobile chat UI + history. Fixed 2026-07-10: mobile-side `configureApi()` was never called/never wired an auth-token getter for the shared API client the coach feature uses, so every coach request failed silently — see `AI_CHANGELOG.md`.
- **Billing**: Stripe checkout session, customer portal, webhook; `subscriptions` table keyed by family; premium gating on courses/lessons/challenges/coach.
- **Notifications**: on-demand weekly digest email (rate-limited endpoint).
- **Accessibility**: light/dark/system themes, high contrast, reduce motion.
- **Admin support access & audit logging** (2026-07-10): manually-seeded `admin` role for consent-gated, time-boxed support sessions only — no standing admin surface. A parent mints a single-use code (`POST /api/family/support-code`, "Get Support Access Code" in mobile Profile settings); an admin redeems it (`POST /api/admin/support-sessions`) for a session scoped to that one family with full parent-equivalent read/write, ending on explicit `POST /api/admin/support-sessions/:id/end` or TTL expiry. `requireAuth` overrides `req.role`/`req.familyId` for the session's duration while `req.actorRole`/`req.userId` keep tracking the real admin for attribution. New `audit_log` table + `logAuditEvent()` records auth, family, and billing security events plus every support-session action; parents read their family's trail via `GET /api/audit-log`. See `docs/SECURITY.md` and `docs/ACCOUNT_MODEL.md`.

## Current Risks

- `replit.md` describes an older, smaller version of the system (6 tables, "no Stripe") — trust `AI_CONTEXT/` docs and the code, not `replit.md`, for feature inventory.
- Duplicate content sources: curriculum exists in both DB tables and `artifacts/mobile/data/seed.ts`; drift is possible.
- **Security gaps**: (Fixed 2026-07-10: `PUT /family/agreement` IDOR, child CRUD ownership checks, session `expires_at` enforcement in `requireAuth`, `DELETE /devices/:deviceId` RBAC (child could de-register any family device — now `requireParent`); full cross-cutting family-data-isolation audit across devices/dashboard/analytics/family/coach/billing/curriculum/notifications found no further gaps; audit logging and the admin role are now implemented — see `AI_CHANGELOG.md`.) See `docs/SECURITY.md` "Known Gaps" for what remains (CORS, email verification).
- **API server will not boot without `STRIPE_SECRET_KEY`**: `src/lib/stripe.ts` throws at import time if the env var is missing, crashing the whole server (not just billing routes). Set the secret or refactor to lazy-init if this becomes a problem.
