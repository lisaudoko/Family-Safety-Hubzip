## 2026-08-08 — Mobile visual redesign: design-token layer + primitives, all 23 screens migrated

- **What**: The user found the app's current look unpolished and asked for a "warm & friendly" visual redesign covering the whole app, while preserving every existing feature. Research confirmed the app had no shared UI primitives at all — `components/UI.tsx` (106 lines) contained only display widgets (`ProgressBar`, `SectionHeader`, `EmptyState`, `PremiumBadge`, `CategoryPill`, `ScoreRing`, `LoadingSpinner`), never a `Button`/`Card`/`Input`/`Badge`; every one of the 23 screens hand-rolled its own `TouchableOpacity` buttons and `TextInput` styling from local `StyleSheet.create` + inline `[styles.x, {color, fontFamily}]` arrays. Font sizes (11–32px) and spacing/radius values were freely hand-picked per screen with no scale. The color palette itself was already solid and warm (`constants/colors.ts`: primary `#F97316` orange, teal `#14B8A6`, cream `#FFFBF5` background, full dark + high-contrast variants) — the plan was to build real infrastructure on top of it, not replace it.

- **Token layer** (`artifacts/mobile/constants/`): `spacing.ts` (4px grid, `xs:4` through `huge:40`), `radius.ts` (`sm:8` through `pill:999`, `lg:16` matches the pre-existing `colors.radius`), `typography.ts` (9-step scale — `display/h1/h2/h3/body/bodyStrong/caption/label/small` — built entirely on the existing Inter weights, no new fonts, distilled from the sizes already in use across the app so migration wouldn't visually drift), `elevation.ts` (three shadow presets using a warm brown-black `#451A03`, not pure `#000`, so shadows read warm rather than corporate-gray — the single biggest lever for "warm" vs. the previous flat 1px-border-only cards), `tabs.ts` (shared `{key, label, featherIcon, sfSymbol, sfSymbolSelected, href}[]` consumed by all three tab-bar render paths — `(tabs)/_layout.tsx`'s native and classic implementations plus the separate `components/BottomTabBar.tsx` — closing an icon/label-drift risk without touching the underlying native-vs-classic architecture), `identityColors.ts` and `agreementColors.ts` (deliberately theme-independent categorical accents — per-child avatar/age-band colors and per-agreement-category colors respectively — extracted from hex values that had been hardcoded inline in `ChildCard.tsx` and `app/agreement.tsx`, with a comment explaining why they're separate from the light/dark palette: they need to stay visually stable across theme changes).

- **Primitives layer** (`artifacts/mobile/components/primitives/`, barrel `index.ts`): `Typography.tsx` (`Display/H1/H2/H3/Body/BodyStrong/Caption/Label/Small`, thin wrappers around the existing `AppText` scaling component — this is what fixes font-scale accessibility, which was silently broken on roughly 22 of 23 screens because they imported raw RN `Text` instead of `AppText`, not just a cosmetic gap); `Button.tsx` (variants `primary/secondary/outline/ghost/destructive`, sizes `sm/md/lg`, built-in `loading`/`disabled`, calls `useHaptics().impact()` internally on every press so screens no longer wire haptics ad hoc, Reanimated press-scale to 0.97 gated by `AccessibilityContext`'s `reduceMotion`); `Card.tsx` (variants `elevated/flat/outline`, optional `pressable` with the same press-scale animation); `Input.tsx` (`TextField`, with a `rightElement` slot added mid-migration once password-visibility-toggle fields needed it); `Badge.tsx` (unifies the old `PremiumBadge`/`CategoryPill` patterns — also fixed a real bug: `PremiumBadge` never called `useColors()` at all and was hardcoded to `#F5A623`, so it never adapted to dark/high-contrast; the replacement uses `colors.warning`); `Toggle.tsx` (`ToggleRow`, wraps RN `Switch`); `SegmentedControl.tsx` (animated sliding indicator, generic over any string-keyed segment list — used for the Learn tab's Courses/Challenges/Assessments picker, age-band pickers, and the accessibility settings screen's theme-mode/text-size pickers); `Avatar.tsx` (circular initials avatar, later gained an optional `onPress` to support the dashboard header's tappable avatar); `ScoreRing.tsx` (rebuilt on `react-native-svg`, which was installed but unused for this — replaces a bordered-`View` circle approximation with a real animated stroke-dashoffset ring, same public API so both call sites (`AssessmentsPanel.tsx`) were drop-in compatible); `Feedback.tsx` (`ProgressBar/SectionHeader/LoadingSpinner/EmptyState`, ported from the old `components/UI.tsx`). Reanimated is used for exactly four touch points total (Button/Card press-scale, SegmentedControl's indicator slide, ScoreRing's fill animation) — all check `settings.reduceMotion` from the same `AccessibilityContext` that `app/_layout.tsx` already used for stack-transition animations, not a new source of truth. `Modal.tsx` (`AppModal`, a bottom-sheet-with-backdrop primitive) was built in the first pass but never gained a real call site — every actual modal in the app turned out to need either a centered confirm dialog (`subscription.tsx`) or native `presentationStyle="pageSheet"` (`profile.tsx`'s edit/verify/support modals), neither of which fit a bottom-sheet pattern — deleted once that became clear rather than left as unused exports.

- **Migration**: all 23 screens plus shared feature components (`ChildCard`, `ChallengeCard`, `CourseCard`, `LessonCard`, `TipCard`, `MonitoringPanel`, `AssessmentsPanel`, `BottomTabBar`, `ErrorFallback`) migrated in risk-ordered batches: foundation → simple screens (`+not-found`, `welcome`, `onboarding`, `coach/history`, `settings/accessibility` — the last one deliberately early since it exercises `ToggleRow`/`SegmentedControl` against real, already-working accessibility state, a good early validation target) → auth flow → tab shell + Home/Learn/Coach → learning flow (course/lesson/quiz) → family/device screens (`family.tsx`, `agreement.tsx`, `challenge/[id].tsx`) → assessments/subscription → profile → `child/[id].tsx` last (667 lines, the most recently reworked and highest-regression-risk screen in the app — migrated in one pass but deliberately kept to leaf-styling changes only, no restructuring of its device-restriction/policy-editing logic). ## 2026-08-08 — Monitoring & device-controls groundwork: effective-policy resolution, family-wide policy UI, real device online status

- **What**: The user asked for parental-monitoring functionality: device online status, location, app install control, time-based app cutoff, bedtime lockdown, and "most time spent on apps," built to Apple's strict privacy rules. Before writing code, researched `docs/POLICY_ENGINE.md`, `docs/DEVICE_ARCHITECTURE.md`, `docs/SECURITY.md`, `AI_CONTEXT/NEXT_TASK.md` Priority 5, and the actual code, and surfaced hard platform constraints via clarifying questions before scoping:
  - Real app blocking / install blocking / bedtime lockdown enforcement on iOS requires Apple's Family Controls entitlement (Screen Time API: FamilyControls/DeviceActivity/ManagedSettings) — native Swift, an Apple approval process, and migrating off Expo Go to a custom dev client/EAS build. Confirmed via `app.json`/`package.json`: this app has none of that (no `eas.json`, no dev-client plugin, no native modules) as of this change.
  - "Phone turned on" isn't a real third-party-app API on iOS; the existing `devices.last_synced_at`/staleness concept is the honest substitute.
  - "Most time spent on apps" isn't real data today: `lib/deviceSync.ts`'s own comment confirms `screen_time` events measure only Digital Village's own foreground time, and the `"activity"` event type (meant for general app usage) has **zero producers** anywhere in the mobile app — `/api/analytics/activity` is wired to nothing.
  - Location tracking is architecturally separate (CoreLocation background permission, its own App Store privacy review).
  - The user decided: build everything that doesn't need the Apple entitlement now; online/last-active status satisfies "phone turned on"; location is deferred entirely; real per-app usage should eventually use Apple's `DeviceActivityReport` extension but isn't fabricated in the meantime.
  - This reframed the actual scope: three already-built "definition only" policy layers (`family_policies`/`child_policies`/`device_restrictions`) had no resolution/merge logic, and the family-wide layer had no mobile UI at all (a gap `NEXT_TASK.md` already flagged) — fixing both is the highest-leverage non-native work available.

- **Backend**:
  - New `services/effectivePolicy.ts`: `getEffectivePolicy(childId, familyId, deviceId?)` resolves `family_policies` → `child_policies` → (only when `deviceId` is passed) `device_restrictions`. Nullable fields (`screen_time_limit_minutes`, `bedtime_start`, `bedtime_end`) use most-specific-layer-wins, matching `docs/POLICY_ENGINE.md`'s documented precedence, and the response says which layer (`source`) supplied each value. Boolean flags (`block_new_app_installs`, `block_safari`, `block_explicit_content`, `require_parent_approval`) are **OR-combined across every layer that has a row** instead — these columns are `NOT NULL DEFAULT false`, so an untouched child/device row is indistinguishable from one where a parent explicitly chose "off"; most-specific-wins would risk a default-`false` row silently overriding a family-level `true`, so OR-combining (response includes `sources: Layer[]`) was chosen as the safer, more-restrictive-leaning behavior. Deliberately does *not* try to merge "most restrictive across all of a child's devices" when no `deviceId` is given — there's no well-defined way to merge, say, two different bedtime windows, so the device layer only applies when the caller asks about one specific device.
  - New route `GET /api/family/children/:childId/effective-policy` (`routes/family.ts`, `requireParent`, family/child-ownership checked via the service, `?deviceId=` optional, 404 if the child or the device-for-that-child isn't found).
  - New `lib/deviceStatus.ts` consolidates `isDeviceStale`/`STALE_AFTER_MS`, which were three separate copy-pasted implementations in `devices.ts`, `dashboard.ts`, and `notifications.ts`. Also adds `deviceStatusLabel(lastSyncedAt): "online" | "recent" | "stale"`, now returned as `syncStatus` alongside the existing `isStale`/`lastSyncedAt` fields on device API responses (`safeDevice` in `devices.ts`, `safeDeviceSummary` in `dashboard.ts`).
  - New `test/effective-policy.test.ts` (8 tests, mirroring `family-policy.test.ts`/`child-policy.test.ts`/`device-restrictions.test.ts` conventions): default-empty resolution, family-value inheritance, child-override-with-fallback, the boolean-OR-not-override behavior specifically, device-layer-only-with-`?deviceId=`, cross-family 404, device-belongs-to-different-child 404, child-session 403. **Not executed** — this dev environment has no `DATABASE_URL`/live Postgres (tests share one real DB per `vitest.config.ts`); typechecked clean but needs a real run before being trusted (flagged in `CURRENT_STATE.md`).

- **Mobile**:
  - New `app/family-policy.tsx` ("Family Defaults" screen) closes the gap `NEXT_TASK.md` explicitly flagged: the `GET|PATCH /api/family/policy` backend route existed with no mobile UI *and no API client wrapper* until now. New `apiGetFamilyPolicy`/`apiUpdateFamilyPolicy` in `lib/apiClient.ts`, new `hooks/useFamilyPolicy.ts` mirroring `useChildPolicy.ts`. Entry point: a new "Family Defaults" card on the parent view of `app/(tabs)/family.tsx`. Registered in `app/_layout.tsx`'s `Stack` (routes here are explicitly listed, not just auto-discovered). Built on the new redesign primitives layer (`components/primitives`, from the in-progress visual redesign — batches 0-2 of that effort landed earlier this session) since this screen didn't exist before and had no legacy styling to preserve.
