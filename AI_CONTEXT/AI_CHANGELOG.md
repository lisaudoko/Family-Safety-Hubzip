## 2026-07-10 — Session expiry enforcement (Priority 6)

- **What**: `requireAuth` (`src/lib/auth-middleware.ts`) now compares `sessions.expires_at` against the current time and rejects with 401 if the session has expired, best-effort deleting the stale row so it doesn't linger in the table. Previously the 90-day TTL was written at session creation (`sessionExpiry()` in `routes/auth.ts`) but never checked at request time — an issued token worked forever until manually deleted (logout, or a parent's `DELETE /family/children/:childId` cascading through `profiles`).
- **Why**: Flagged as a known risk in `AI_CONTEXT/CURRENT_STATE.md` since the documentation system's creation (2026-07-08) and listed as a required Priority 6 item before production. Small, well-defined, no product-scope ambiguity — picked as the next task after finishing the family/device/education passes.
- **Files affected**: `artifacts/api-server/src/lib/auth-middleware.ts`, `artifacts/api-server/test/auth.test.ts` (new — 3 tests), `docs/SECURITY.md`.
- **Future considerations**: Sessions aren't refreshed/rotated on activity — a still-active user gets logged out exactly 90 days after their original login/registration, not 90 days after last use. Not addressed here (would be a product decision on session-refresh UX); flagged for a future pass if it becomes a support complaint.

## 2026-07-10 — Split education activity into a dedicated device-event type (Priority 1/7)

- **What**: Resolved the "ingest educational activity events through the device-event pipeline vs. keep separate in `user_progress`" pending decision (product owner chose: ingest via device-event pipeline). Investigation showed this was already substantially wired — `FamilyContext.tsx` was already calling `submitActivityEvent()` on every lesson/quiz/challenge/assessment completion (`artifacts/mobile/context/FamilyContext.tsx:462,469,494,518,541`) — but it posted a generic `activity` device event, indistinguishable from other app activity, and the schema's `lesson_participation` capability (declared in `lib/capabilities.ts` since before this session) was never actually wired to any event type. Added `education_activity` as its own event type mapped to `lesson_participation`; `submitActivityEvent()` in `deviceSync.ts` now posts that type instead of generic `activity`. Added `GET /api/analytics/education` (mirrors `/activity`), added `education` to `GET /api/analytics/summary`, and added an `education` breakdown to `GET /api/dashboard/children/:childId` plus an `educationCount` to `GET /api/dashboard/overview`'s per-child `recentActivity`. `getActivitySummary` in `lib/analytics.ts` was refactored into a shared `summarizeActivityLikeEvents` helper parameterized by event type, with a new `getEducationActivitySummary` wrapper, to avoid duplicating the aggregation logic.
- **Why**: Product owner explicitly chose the device-event pipeline route. `user_progress` remains the correct source of truth for detailed progress state (percentages, badges, scores) — this change only adds a lightweight completion *signal* to the existing device_events/analytics infrastructure so the dashboard's activity timeline can include education activity without a bespoke join.
- **Files affected**: `artifacts/api-server/src/lib/capabilities.ts`, `artifacts/api-server/src/lib/analytics.ts`, `artifacts/api-server/src/routes/analytics.ts`, `artifacts/api-server/src/routes/dashboard.ts`, `artifacts/api-server/src/routes/devices.ts` (`validateEventPayload` extended to accept `education_activity` payloads), `artifacts/api-server/test/analytics.test.ts` (+9 tests), `artifacts/api-server/test/dashboard.test.ts` (extended existing tests), `artifacts/mobile/lib/deviceSync.ts`, `docs/API.md`, `docs/DEVICE_ARCHITECTURE.md`.
- **Future considerations**: "Connect education progress to parent dashboard" (Priority 7) is only partially done — the dashboard now shows education *activity counts*, not detailed progress state (course %, badge counts, assessment scores) from `user_progress`. That would need a separate dashboard query joining `user_progress`, not the device-events pipeline.

## 2026-07-10 — Child Family Experience + family API ownership hardening

- **What**: Implemented Priority 4's "Child Family Experience" from `NEXT_TASK.md`. `GET /api/family` now returns a `siblings` field (same list as `children`, self-excluded for child sessions). `GET /api/family/agreement` now resolves the family via the session's `req.familyId` instead of `families.parent_id`, so child sessions can finally read the agreement (previously always got `agreement: null`). `PUT /api/family/agreement` now requires `requireParent` and checks the supplied `familyId` matches `req.familyId` (403 otherwise) — fixes a pre-existing IDOR. `POST /family/children`, `PATCH /family/children/:childId`, `DELETE /family/children/:childId` now verify family ownership before acting (403/404) — fixes the other pre-existing IDOR gaps flagged under Priority 6. NEXT_TASK.md's own checklist for this feature calls for an authorization review, which surfaced real IDOR gaps also tracked under Priority 6 — user approved fixing both in one pass.
- **Files affected**: `artifacts/api-server/src/routes/family.ts`, `artifacts/api-server/test/family.test.ts` (new — 8 tests), `artifacts/mobile/context/FamilyContext.tsx`, `artifacts/mobile/lib/apiClient.ts`, `artifacts/mobile/app/(tabs)/family.tsx`, `docs/API.md`, `docs/SECURITY.md`.
