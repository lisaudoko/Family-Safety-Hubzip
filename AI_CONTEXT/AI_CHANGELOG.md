## 2026-07-10 — Coach chat fix + per-child devices/monitoring on Family tab

- **What**: Two fixes.
  (1) **Coach bug**: `POST /api/coach/chat` was actually working correctly server-side (verified with a live curl round-trip: register parent, create family, send message, real AI reply returned). The bug was entirely mobile-side: the coach feature is the only screen routed through the shared generated client (`@workspace/api-client-react`'s `customFetch`, via `useSendCoachMessage`), which requires `configureApi()` (`artifacts/mobile/lib/api.ts`) to set a base URL and auth-token getter before use. `configureApi()` was defined but never called anywhere (`app/_layout.tsx` only called the separate legacy client's `configureApiBase()`), and even if called, its body never wired up `setAuthTokenGetter` at all — so every coach request went out with no base URL and no `Authorization` header, failing on every single message. Fixed by wiring `setAuthTokenGetter(getToken)` into `configureApi()` (reusing `lib/apiClient.ts`'s existing `getToken`) and calling `configureApi()` from `app/_layout.tsx` alongside `configureApiBase()`. Also stopped `CoachContext.tsx`'s blanket `catch { setSendError(genericMessage) }` from swallowing the real error — now surfaces the actual server error message (e.g. free-tier-limit 403 text) via `ApiError`, newly exported from `@workspace/api-client-react`, falling back to the generic message only for truly unexpected errors.
  (2) **Per-child devices & monitoring on the Family tab**: previously a parent had to go to the Profile tab, pick a device from a flat family-wide list, and edit restrictions there — disconnected from the Family tab's existing per-child list/detail screen (`app/child/[id].tsx`). Added a "{child}'s Default Restrictions" section (bound to the `child_policies` endpoints added in the prior session, via new `useChildPolicy` hook and `apiGetChildPolicy`/`apiUpdateChildPolicy`/`ChildPolicy` in `apiClient.ts` — this was greenfield mobile work, no client code existed for these routes yet) and a "Devices" section (new `useChildDevices` hook, filters `apiGetDevices()` client-side by `ownerId === childId` — no new endpoint needed) directly on each child's detail screen. Each device row is renameable in place (pencil icon → inline `TextInput` → `apiUpdateDevice(deviceId, { name })`, which was already fully implemented server+client but had no UI anywhere) and expands to that device's own restrictions (reusing the existing `useDeviceRestrictions` hook). Removed the "Select Device" + "Device Restrictions" sections from `app/(tabs)/profile.tsx` entirely (and the now-dead `selectedDeviceId`/`devices` state and effect), since the whole point was to stop needing the Profile tab for this.
- **Why**: Coach bug was reported as broken on every message — root-caused via direct server testing rather than assumption, confirming the server/LLM path was healthy and narrowing to the mobile client config gap. The Family tab change was an explicit product-owner UX request: monitoring should live with the child it belongs to, not require a trip to a different tab and a device picker; devices should be nameable so parents can tell whose is whose.
- **Files affected**: `artifacts/mobile/lib/api.ts`, `artifacts/mobile/app/_layout.tsx`, `artifacts/mobile/context/CoachContext.tsx`, `lib/api-client-react/src/index.ts` (export `ApiError`/`ResponseParseError`), `artifacts/mobile/lib/apiClient.ts` (new `ChildPolicy` type + `apiGetChildPolicy`/`apiUpdateChildPolicy`), `artifacts/mobile/hooks/useChildPolicy.ts` (new), `artifacts/mobile/hooks/useChildDevices.ts` (new), `artifacts/mobile/app/child/[id].tsx` (new `RestrictionRows`/`DeviceRow` components + sections), `artifacts/mobile/app/(tabs)/profile.tsx` (removed device picker/restrictions UI and its now-dead state).
- **Future considerations**: No backend changes were needed — all endpoints already existed and were tested (`GET /api/devices`, `PATCH /api/devices/:deviceId`, `GET|PATCH /api/devices/:deviceId/restrictions`, `GET|PATCH /api/family/children/:childId/policy`). ## 2026-07-10 — Admin support-access sessions + security audit logging (Priority 6, closes it out)

- **What**: Completed the three remaining Priority 6 items. (1) **RBAC fix**: `DELETE /api/devices/:deviceId` was `requireAuth`-only, letting a child de-register any device in their family (including a parent-managed monitoring device); now `requireParent`. (2) **Admin role**: added a manually-seeded `admin` `profiles.role`, used exclusively for consent-gated, time-boxed support access — not a standing admin surface. A parent mints a single-use, ~30min-TTL code via `POST /api/family/support-code` (new "Get Support Access Code" row in mobile Profile settings, `app/(tabs)/profile.tsx`). An admin redeems it via `POST /api/admin/support-sessions`, getting a fresh Bearer token (own `sessions` row, `support_session_id` set, 60min TTL) that `requireAuth` resolves to `req.role = 'parent'` and the target family's `req.familyId` — reusing every existing `requireParent`-gated route unmodified — while `req.actorRole`/`req.userId` keep tracking the real admin identity. `POST /api/admin/support-sessions/:id/end` ends it early. New `requireAdmin` middleware checks `req.actorRole` (not the overridable `req.role`), so it still gates correctly even when called via a support-session token. (3) **Audit logging**: new `audit_log` table + `logAuditEvent()` helper (`src/lib/audit.ts`), called explicitly at auth (register/login/login-failed/child-login/child-login-failed/logout/password-reset-requested/completed), family (family-created/child-added/child-updated/child-removed/agreement-updated), and billing (checkout-session-started/portal-session-opened) call sites, plus support-session lifecycle (`support_code_created`/`support_session_started`/`support_session_ended`). A `logSupportSessionWrite` middleware (mounted globally in `app.ts`, gated on `req.isSupportSession` — checked inside `res.on('finish', ...)` since it runs before per-router `requireAuth`) auto-logs every mutating request made during an active support session. `GET /api/audit-log` (`requireParent`) gives a family-scoped, paginated, date-filterable read. CSRF is confirmed N/A (Bearer-token API, no cookies) and needs no further action unless cookies are introduced.
- **Why**: Product owner wanted admin access reserved strictly for a support scenario — "the parent account can give us a code for us to put in to login with and we can fix the errors" — not a general admin panel. Every action taken during such access must be traceable back to the specific admin and visible to the family, which drove both the actorRole/role-split design and the audit log.
- **Files affected**: `lib/db/src/schema/index.ts` (`support_codes`, `support_sessions`, `audit_log` tables; `sessions.support_session_id`), `artifacts/api-server/src/lib/startup-migrate.ts` (mirrored idempotent migrations), `artifacts/api-server/src/lib/auth-middleware.ts` (support-session resolution in `requireAuth`, new `requireAdmin`, `AuthRequest.actorRole`/`isSupportSession`), `artifacts/api-server/src/lib/audit.ts` (new), `artifacts/api-server/src/routes/admin.ts` (new), `artifacts/api-server/src/routes/index.ts` (mount ordering — `adminRouter` before `dashboardRouter`, which is the sole router that blanket-applies `requireParent` and would otherwise 403 admin requests before they reach `adminRouter`), `artifacts/api-server/src/routes/devices.ts` (RBAC fix), `artifacts/api-server/src/routes/family.ts` (support-code mint, audit-log read, `logAuditEvent` calls, and a bug fix: `GET /api/family` previously re-derived the caller's own profile/family instead of using `req.familyId`, so it always returned `family: null` during a support session — now uses `req.familyId`/`req.actorRole` directly), `artifacts/api-server/src/routes/billing.ts` (`logAuditEvent` calls), `artifacts/api-server/src/app.ts` (mounted `logSupportSessionWrite`), `artifacts/api-server/test/helpers.ts` (`createAdmin`), `artifacts/api-server/test/admin.test.ts` (new — 8 tests), `artifacts/mobile/lib/apiClient.ts` (`apiCreateSupportCode`), `artifacts/mobile/app/(tabs)/profile.tsx` (Get Support UI: code + live expiry countdown, parent-only), `docs/SECURITY.md`, `docs/ACCOUNT_MODEL.md`, `docs/API.md`.
